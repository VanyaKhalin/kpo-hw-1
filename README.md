# ВышКат — учёт транспорта и оборудования

Консольное приложение на Java для домашнего задания № 1 по КПО. В нём можно добавлять транспорт и оборудование, проводить техосмотр и смотреть отчёты.

Выполнял: Халин Иван Бпи258
## Запуск приложения

Нужны **IntelliJ IDEA и JDK 25**. JUnit уже находится в папке `lib`, скачивать его отдельно не нужно.

Откройте [Main.java](src/Main.java) и нажмите зелёную кнопку рядом с методом `main`.

При запуске склад пустой. Данные вводятся через консоль. Чтобы выйти, выберите `0` в главном меню.

### Если IDEA не распознала настройки

- В **Project Structure → Modules → Sources** отметьте `src` как **Sources**, а `tests` как **Tests**.
- Если JUnit не подключён, откройте **Project Structure → Modules → Dependencies → + → JARs or directories**. Выберите JAR из `lib` и поставьте область **Test**.
- Проверьте, что в настройках проекта выбран **JDK 25**.

## Что умеет приложение

| Пункт меню | Действие |
| --- | --- |
| 1 | Добавить транспорт после техосмотра |
| 2 | Добавить оборудование |
| 3 | Показать количество транспорта и расход энергии за сутки |
| 4 | Показать весь транспорт: ID, вид, версия и цвет |
| 5 | Показать количество и список транспорта для новичков |
| 6 | Показать количество и список оборудования |
| 7 | Показать всё имущество: ID и название |
| 0 | Выйти |

Доступны велосипед, электровелосипед и электросамокат. Из оборудования - шлем, зарядный шкаф и док-станция. В отчётах используются названия классов, например `Bicycle` и `Helmet`.

Чтобы добавить транспорт, нужно выбрать его вид, ввести версию, выбрать цвет по номеру и указать простоту использования. Для электрического транспорта и оборудования также нужно ввести расход энергии за сутки в кВт·ч.

### Правила и проверки

- ID создаются автоматически: `T-1`, `T-2`, и тд для транспорта и `E-1`, `E-2`, и тд для оборудования. Для каждой группы есть свой счётчик.
- Простота использования задаётся числом от **1 до 10**. Транспорт с простотой **6 и выше** подходит новичкам.
- Версия должна быть больше нуля. Техосмотр пропускает транспорт только с версией **3 и выше**.
- Жёлтый и чёрный транспорт не проходит техосмотр. Эти правила я выбрал сам: в ТЗ конкретные цвета и версии не указаны.
- Сначала проверяется цвет, потом версия. Если причин отказа несколько, показывается первая.
- `inspectTransport()` возвращает `true`, если транспорт принят. При отказе транспорт не попадает на склад.
- Расход энергии не может быть отрицательным, бесконечным или `NaN`. Можно вводить `2.5` или `2,5`.
- Нельзя добавить `null` или повторно добавить объект с тем же ID.
- При неправильном вводе консоль просит ввести значение ещё раз. Конструкторы и склад сообщают об ошибках через `IllegalArgumentException`.

Общий расход энергии считается для электрического транспорта и оборудования на складе. Велосипед и шлем в эту сумму ничего не добавляют. Отклонённый транспорт тоже не учитывается.

## Как устроен код

| Папка или класс | За что отвечает |
| --- | --- |
| [transport](src/transport) | Классы транспорта и интерфейс `ITransport` |
| [equipment](src/equipment) | Классы оборудования и интерфейс `IEquipment` |
| [warehouse](src/warehouse) | Хранение транспорта и оборудования, проверка повторного добавления |
| [servicecenter](src/servicecenter) | Техосмотр и причины отказа |
| [inventory](src/inventory) | Добавление имущества, подсчёты и отчёты |
| [console](src/console) | Меню, ввод и вывод |
| [di](src/di) | Контейнер, который создаёт и хранит нужные объекты |
| [Main](src/Main.java) | Настройка зависимостей и запуск приложения |

`Bicycle` наследуется от `Transport`. `ElectricBicycle` и `ElectricScooter` наследуются от `ElectricTransport`, который тоже является наследником `Transport`.

С оборудованием похожая схема: `Helmet` наследуется от `Equipment`, а `ChargingCabinet` и `DockingStation` - от `ElectricEquipment`.

Общие поля и проверки находятся в базовых классах, чтобы не писать одно и то же несколько раз. Поля свойств объявлены `final`. ID можно получить через `ITransport.getTransportID()` и `IEquipment.getEquipmentID()`.

Один склад хранит и транспорт, и оборудование. Это одна задача - хранение имущества. Техосмотр и отчёты вынесены в другие классы.

При добавлении транспорта `ConsoleApp` обращается к `InventoryService`. Тот вызывает техосмотр и добавляет транспорт на склад только при положительном результате. Причину отказа определяет `ServiceCenter`, а сообщение пользователю выводит `ConsoleApp`.

## SOLID

### S - у каждого класса своя задача

`Warehouse` хранит имущество, `ServiceCenter` проверяет транспорт, `InventoryService` считает данные и готовит отчёты, а `ConsoleApp` работает с пользователем. Например, текст меню можно поменять, не трогая техосмотр.

### O - возможность добавлять новое без больших изменений

Можно создать новый класс транспорта на основе `Transport` или `ElectricTransport`. Склад и отчёты смогут работать с ним через `ITransport`. Для электрического наследника расход энергии уже будет учитываться.

### L — наследники могут использоваться вместо общего типа

Склад, техосмотр и отчёты принимают `ITransport`, поэтому могут работать и с велосипедом, и с электросамокатом. Все они возвращают ID, версию, цвет и простоту использования с одинаковым смыслом. Оборудование так же используется через `IEquipment`.

Новый класс должен соблюдать эти правила: например, его ID не должен меняться после создания.

### I — интерфейсы содержат только нужные методы

Для транспорта, оборудования, склада и техосмотра есть отдельные интерфейсы. Поэтому шлему не нужны методы цвета или версии транспорта. Методы ввода и печати тоже не входят в интерфейсы имущества.

### D — зависимости передаются снаружи

`InventoryService` получает `IWarehouse` и `IServiceCenter` в конструкторе. Он не создаёт склад и техосмотр сам. Нужные классы выбираются в `Main`, а в тестах вместо настоящего техосмотра можно передать подмену.

`ConsoleApp` получает `InventoryService` и `Scanner` таким же способом. Для `InventoryService` отдельный интерфейс пока не нужен, потому что у него одна реализация.

## DI-контейнер

В проекте есть небольшой [DIContainer](src/di/DIContainer.java). Метод `register()` запоминает, как создать объект нужного типа. Метод `get()` создаёт его при первом обращении и сохраняет. При повторном обращении возвращается тот же объект.

В `Main` регистрируются склад, техосмотр, `Scanner`, `InventoryService` и `ConsoleApp`. При создании сервисов контейнер передаёт им нужные зависимости.

### Как подменяется техосмотр

[FakeServiceCenter](tests/support/FakeServiceCenter.java) — простой тестовый класс. Он реализует `IServiceCenter` и всегда возвращает результат, который мы передали в его конструктор: `true` или `false`.

`addsTransportWhenFakeInspectionApproves()` проверяет добавление при ответе `true`. Даже жёлтый велосипед версии 1 добавляется: так мы убеждаемся, что `InventoryService` доверяет переданному техосмотру. `doesNotAddTransportWhenFakeInspectionRejects()` проверяет отказ при ответе `false`.

В `usesFakeInspectionRegisteredInContainer()` подмена регистрируется в DI-контейнере вместо настоящего техосмотра.

`countsTransportForBeginnersStartingAtEaseSix()` проверяет границу: простота 5 не подходит новичкам, а 6 уже подходит.

## Пример работы

1. После запуска выберите пункты `3`–`7`. Склад пустой, поэтому количества и расход энергии равны нулю.
2. Через пункт `1` добавьте транспорт из таблицы. Сначала вводится вид, затем версия, цвет, простота и энергия, если она нужна.

| Транспорт | Номер вида | Версия | Цвет | Простота | Энергия |
| --- | --- | --- | --- | --- | --- |
| Велосипед | 1 | 3 | 2 — зелёный | 5 | Не нужна |
| Электровелосипед | 2 | 3 | 3 — синий | 6 | 1,5 |
| Электросамокат | 3 | 4 | 5 — белый | 8 | 2,5 |

3. Через пункт `2` добавьте шлем (вид `1`), зарядный шкаф (вид `2`, энергия `3`) и док-станцию (вид `3`, энергия `1`).
4. Проверьте отчёты: должно быть **3 транспорта**, **2 транспорта для новичков**, **3 единицы оборудования** и **8 кВт·ч в сутки**. Общий отчёт покажет все **6 объектов** с их ID.
5. Попробуйте добавить жёлтый транспорт версии 3, чёрный версии 3 и зелёный версии 2. Укажите простоту `7`. Все три будут отклонены, количество имущества не изменится.
6. Введите букву вместо номера меню, `11` вместо простоты или `-1` вместо энергии. Программа попросит повторить ввод.
7. В подменю добавления выберите `0`, чтобы вернуться. В главном меню `0` завершает программу.

ID смотрите в выводе программы: после отказов в нумерации могут быть пропуски. Повторное добавление одного объекта проверяется в `WarehouseTest`. Если ввод закончился, приложение завершает работу.

## Ответы на вопросы из ТЗ

### Какой принцип SOLID виден лучше всего?

**DIP** в [InventoryService](src/inventory/InventoryService.java). Склад и техосмотр передаются в конструктор через интерфейсы. Благодаря этому в тестах можно заменить настоящий техосмотр на `FakeServiceCenter`.

### Какой принцип соблюдён не полностью и почему?

Подсчёт энергии зависит от двух классов: `ElectricTransport` и `ElectricEquipment`. Если добавить потребителя энергии вне этих классов, этот метод придётся изменить.

### Что нужно будет изменить при расширении?

- **Новый транспорт:** добавить класс и пункт создания в меню. Склад и обычные отчёты продолжат работать. Наследник `ElectricTransport` попадёт и в подсчёт энергии.
- **Сотрудник:** сделать отдельные классы и сервис учёта. По ТЗ сотрудники не являются имуществом, поэтому в списки транспорта и оборудования они не попадут.
- **Склад запчастей:** отдельную вещь с ID можно учитывать как оборудование. Для партий запчастей с количеством понадобится отдельная модель склада. Новые сервисы нужно подключить в `Main`, а нужные действия добавить в меню.

### Какие тесты проверяют техосмотр и правило для новичков?

[ServiceCenterTest](tests/servicecenter/ServiceCenterTest.java) проверяет правила настоящего техосмотра. В [InventoryServiceTest](tests/inventory/InventoryServiceTest.java) методы `addsTransportWhenFakeInspectionApproves()` и `doesNotAddTransportWhenFakeInspectionRejects()` проверяют, как сервис учёта реагирует на его ответ. Метод `countsTransportForBeginnersStartingAtEaseSix()` проверяет правило для новичков.

Подмена передаётся в конструктор или через контейнер. Второй вариант проверяется в [DIContainerTest](tests/di/DIContainerTest.java), в методе `usesFakeInspectionRegisteredInContainer()`.
